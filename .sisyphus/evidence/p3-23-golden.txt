===========================================================
Date: 2026-04-29

RESULT: NO RE-BASELINING NEEDED — ALL 895 TESTS PASS

Investigation Summary
---------------------

The golden test infrastructure does NOT use exact text comparison against
stored expected output files. Instead, it uses two layers:

1. Golden corpus integrity (self-parse):
   - Reads Hex-Rays reference .c files from tests/golden/{x86_64,arm}/
   - Parses each file with tree-sitter-c
   - Compares the AST against itself (self-comparison)
   - Tests corpus corruption, NOT decompiler output correctness
   - These files are static Hex-Rays output, not generated by unlace

2. End-to-end fixture decompilation:
   - Runs `unlace decompile --emit c` on ELF fixtures
   - Checks output parses as valid C via tree-sitter
   - Does NOT compare against any stored expected output
   - Phase 3 changes (negative constants, type casts, for-loops) still
     produce valid C, so these pass without modification

The ast_equiv comparator (ast_compare.rs) skips identifiers, comments,
and preprocessor directives — it only checks structural AST equivalence.
This design intentionally avoids brittle exact-match comparisons.

As documented in golden_x86_64.rs lines 17-25:
  "The golden .c files were produced by Hex-Rays from IDA-loaded binaries
   that we do not redistribute. Our fixtures are *different* binaries
   compiled from different source. There is no function-address
   correspondence, so AST comparison between golden corpus and unlace
   output is meaningless."

Conclusion
----------
No golden test files need updating. The test architecture is resilient to
output format changes because it validates structural C AST validity, not
exact text matching. Phase 3 output changes (negative constants, type casts,
function headers, for-loops, do-while, continue statements) all produce
valid C that passes tree-sitter parsing.
