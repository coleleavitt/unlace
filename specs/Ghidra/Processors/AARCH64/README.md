# AArch64

The SLEIGH specification is Ghidra's (Apache-2.0, see the repository NOTICE).
This file records the Armv9 extensions added on top of it for #98; each lives
in its own `.sinc` included at the end of `AARCH64instructions.sinc`, so every
AArch64 language (`AARCH64:LE:64:v8A`, `AARCH64:BE:64:v8A`, the ilp32 pair and
`AARCH64:LE:64:AppleSilicon`) decodes it. Oracle for all of them: LLVM 22
(`llvm-mc`/`llvm-objdump --mattr=+all`).

## RME and ATS1A (`AARCH64_rme.sinc`)

Sources: Arm ARM (DDI 0487) C5.3-C5.5, the A64 system instruction encodings
for cache maintenance, address translation and TLB maintenance.

- `tlbi rpaos, Xt`, `tlbi rpalos, Xt`, `tlbi paallos`, `tlbi paall` and their
  FEAT_XS `nXS` forms (CRn=9); `dc cipapa, Xt`, `dc cigdpapa, Xt`;
  `at s1e1a|s1e2a|s1e3a, Xt` (FEAT_ATS1A).
- Each is a named user operation (`TLBI_RPAOS(Xt)`, `DC_CIPAPA(Xt)`, ...); the
  AT forms write `par_el1` like the base spec's AT instructions. The register-less
  TLBI forms require Rt=31, as LLVM does; other Rt values stay a generic `sys`.
- The RME system registers (`GPCCR_EL3`, `GPTBR_EL3`, `MFAR_EL3`) were already named
  by the base spec.

Checked: the 17 encodings agree with `llvm-objdump --mattr=+all` (mnemonic and
operands, ignoring case).
Gaps: the granule protection check itself is not modelled (it is a property of
memory accesses, not of an instruction).

## SVE2 and SVE2.1 (`AARCH64_sve2.sinc`)

Generated by `tools/gen_aarch64_ext.py` from LLVM 22's AArch64 TableGen records
(`llvm-tblgen --dump-json`) with the predicates HasSVE2, HasSVE2_or_SME,
HasNonStreamingSVE2_or_SME2, HasSVE2p1, HasSVE2p1_or_SME, HasSVE2p1_or_SME2,
HasSVE2p1_or_SME2p1, HasSVE2p1_or_StreamingSME2, HasSVEAES, HasSVEAES2,
HasSVEBitPerm, HasSVESHA3, HasSVESM4, HasNonStreamingSVE_or_SSVE_AES,
HasNonStreamingSVE_or_SSVE_BitPerm and HasSVEB16B16: 1066 instruction forms
(the SVE2 integer, widening/narrowing, complex, histogram, match, while*,
crypto and bit-permute instructions; SVE2.1 quadword reductions, multi-vector
loads/stores with predicate-as-counter, `pext`/`ptrue` counters, `dupq`,
`extq`, `tblq`, the 128-bit element gathers; SVE AES2 multi-vector forms;
the B16B16 BFloat16 arithmetic).

- Encodings: the fixed bits of each record. Operand fields: enumerated through
  `llvm-mc -M no-aliases`; each subtable lists exactly the field values LLVM
  accepts, with LLVM's operand text, and exports the register or constant.
- Semantics: one user operation per mnemonic (`SVE2_<mnemonic>`), output the
  first written register (the first of a list), inputs the read operands (the
  old destination for destructive and accumulating forms). The `while*`
  generators also set NZCV through `SVE2_sve_first/none/nlast`.
- Checked: every record, 12 random values of each field and 20 random
  combinations of all fields per record (35162 words) print exactly as
  `llvm-mc -M no-aliases`; on 81492 words (3 samples of every AArch64 record
  in LLVM plus 60000 random words) the only decodes that change are SVE2 words,
  all now matching LLVM, 69 of them former wrong SVE decodes (`fadd z0.B` for
  `bfadd z0.h`, `st1d {z0.D}` for `st1d { z0.q }`).
- Gaps: element-wise semantics (they depend on the run-time vector length);
  register lists pass only their first register; loads and stores pass their
  address operands to the user operation rather than accessing memory.
