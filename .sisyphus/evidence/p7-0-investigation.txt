================================================================================
P7-0: 0-IFs ROOT CAUSE INVESTIGATION
================================================================================

Date:     2026-04-30
Subject:  debug_calls.elf, debug_structs.elf produce 0 if-branches
Verdict:  ROOT CAUSE = LIFTER (primary) + FUNCTION_DISCOVERY (secondary)
Severity: Two distinct bugs, both real, neither fatal

================================================================================
1. EXECUTIVE SUMMARY
================================================================================

The 0-ifs result is NOT a structurer or CFG bug. The pipeline (lifter →
CFG → structurer) correctly produces if-blocks WHENEVER a CBRANCH IR
instruction exists in the function. The problem is that, for these two
fixtures, no CBRANCH gets emitted into ANY user function:

  * debug_calls.elf — User-code conditionals are compiled by GCC -g -O0
    into branchless `cmov` (conditional move) instructions, NOT into
    `Jcc` (conditional jump) instructions. The unlace lifter currently
    treats every Cmov* mnemonic as a plain MOV, dropping the condition
    entirely. → LIFTER bug.

  * debug_structs.elf — The user functions (`area`, `offset`, `main`)
    contain no conditionals at all in source. The 7 Jcc instructions
    that exist in the binary live in unnamed CRT helper code
    (deregister_tm_clones / register_tm_clones / __do_global_dtors_aux),
    which has no .symtab entries and is therefore invisible to unlace's
    symbol-driven function discovery. → FUNCTION_DISCOVERY gap, but
    no user-visible effect because these helpers are noise anyway.

medium.elf works (37 ifs in output) because the inlined -O2 code paths
emit ordinary `Jcc` instructions which the lifter handles correctly.

2. RAW EVIDENCE
================================================================================

  debug_calls.elf   : 697 lines,  0 ifs, 7 returns,  0 CBRANCH,  12 functions
  debug_structs.elf : 199 lines,  0 ifs, 2 returns,  0 CBRANCH,   4 functions
  calls.elf  (-O2)  : 145 lines,  0 ifs,                          3 functions
  medium.elf (-O2)  : 947 lines, 37 ifs,                          5 functions

(`calls.elf` -O2 also has 0 ifs because static helpers are inlined into

  debug_structs.elf : 7 Jcc instructions, 0 cmov instructions
  calls.elf         : 7 Jcc instructions, 2 cmov instructions
  medium.elf        : 108 Jcc instructions, 8 cmov instructions

No symbols cover 0x1070-0x1128. unlace's `discover_functions` in

helpers with no symbols. User functions `area`, `offset`, `main` have
0 Jcc and 0 cmov.

------ 2.4  Where do the user-code conditionals go? ------

calls.c source contains ternary conditionals:

    int max(int a, int b) { return a > b ? a : b; }    // line 7
    int min(int a, int b) { return a < b ? a : b; }    // line 8
    int clamp(int x, int lo, int hi) { ... }           // line 9

GCC -g -O0 compiles these to BRANCHLESS code using `cmov`:

  abs_val:                          max:
    11bf: mov  %edi,-0x4(%rbp)        11d6: mov  %edi,-0x4(%rbp)
    11c2: mov  -0x4(%rbp),%eax        11d9: mov  %esi,-0x8(%rbp)
    11c5: mov  %eax,%edx              11dc: mov  -0x8(%rbp),%edx

                                      11e8: ret

Three cmov instructions in user code: cmovns @ 0x11c9 (abs_val),
cmovge @ 0x11e4 (max), cmovle @ 0x11ff (min).

================================================================================
3. PIPELINE WALK — WHERE INFORMATION GETS LOST
================================================================================

------ 3.1  Lifter (crates/unlace-lift-x86/src/lift.rs:275-280) ------

  match insn.mnemonic() {
      M::Mov | M::Movzx | M::Movsx | M::Movsxd | M::Cmove | M::Cmovne
      | M::Cmovb | M::Cmovae | M::Cmova | M::Cmovbe | M::Cmovl
      | M::Cmovge | M::Cmovg | M::Cmovle | M::Cmovs | M::Cmovns => {
          data_move::lift_mov(ctx, insn);     // <-- PROBLEM
      }

`lift_mov` (data_move.rs:8-25) emits an unconditional COPY:

      ctx.emit(IrInsn::with_output(IrOp::Copy, dst, smallvec![src],
                                   ctx.addr));

The condition flag is silently discarded. The IR for abs_val therefore
contains:
      neg edx              -> INT_2COMP edx
      cmovns edx,eax       -> COPY eax = edx       <-- always copies!

There is NO CBRANCH and NO conditional select. The structurer cannot
recover an if/ternary from this — the information is gone.

For comparison, Jcc handling IS correct:
      lift.rs:325-328 → control_flow::lift_jcc → emits IrOp::Cbranch
      control_flow.rs:36-46 — produces a proper CBRANCH with a
      synthesised boolean condition derived from ZF/SF/CF/OF.

------ 3.2  CFG (crates/unlace-ir/src/cfg.rs:201-223) ------

CBRANCH terminators correctly produce two edges:

      Some(IrOp::Cbranch) => {
          ... add_edge(... EdgeKind::ConditionalTrue);
          ... add_edge(... EdgeKind::ConditionalFalse);
      }

If no CBRANCH is emitted (cmov case), the CFG simply has linear
unconditional edges. Working correctly given its inputs.

------ 3.3  Structurer (crates/unlace-struct/src/structurer.rs) ------

  fn block_has_cbranch(&self, bid: BlockId) -> bool {           // L1062
      self.func.function.blocks.get(&bid)
          .and_then(|b| b.insns.last())
          .is_some_and(|insn| insn.op == IrOp::Cbranch)
  }

If-/loop-recognition keys off Cbranch terminators (L398, L666, L734-740,
L1068). With no Cbranch in any block of these functions, no if-region
is ever produced. Working correctly given its inputs.

------ 3.4  Function discovery (crates/unlace-cli/src/pipeline.rs:29-72) ------

Symbol-driven first (`SymbolKind::Function && sym.size > 0`), prologue
scan only as fallback ("if funcs.is_empty()"). Since debug_calls.elf
has 11 user symbols, the fallback never runs and the unnamed CRT
helpers are never decompiled. Their 6 Jcc instructions never enter the
pipeline. (Marginal issue — these helpers don't matter for user code.)

================================================================================
4. CLASSIFICATION
================================================================================

PRIMARY ROOT CAUSE: LIFTER

  Issue:    All Cmov* x86 mnemonics are routed to lift_mov(), which
            emits an unconditional Copy and discards the condition.
  Location: crates/unlace-lift-x86/src/lift.rs:275-280
            crates/unlace-lift-x86/src/ops/data_move.rs:8-25
  Effect:   Conditional moves silently become unconditional moves in
            IR. Source ternaries (?:) compiled with -O0/-O1 vanish.
  Impact:   debug_calls.elf — abs_val, max, min, clamp lose all
                              conditional logic; outputs all show
                              return value of zero.
            calls.elf -O2  — abs_val/max/min are inlined into
                              compute; the inlined cmov sequences
                              also become unconditional.
            medium.elf      — has 8 cmov instructions; some control
                              decisions are silently lost (but the
                              108 Jcc dominate, so 37 ifs survive).

  Idiomatic fix: a Cmov instruction should lower to either
                   (a) IrOp::Cbranch + 2 BBs producing a proper if, or
                   (b) a select-style IR primitive (Cbranch+phi or
                       a dedicated INT_CONDITIONAL/CMOVE op) that the
                       structurer can recognise as a ternary.
                 The condition is constructible from existing flag
                 helpers in control_flow.rs::jcc_condition (cmovge ↔
                 jge condition, cmovns ↔ jns condition, etc.); the
                 mnemonic-to-condition map is trivial because Cmov
                 cc and Jcc cc share the same condition codes.

SECONDARY ROOT CAUSE: FUNCTION_DISCOVERY

  Issue:    Symbol-driven discovery skips prologue-scan whenever any
            function symbols exist, leaving unnamed CRT helpers
            (deregister_tm_clones, register_tm_clones,
            __do_global_dtors_aux, frame_dummy) undiscovered.
  Location: crates/unlace-cli/src/pipeline.rs:29-58
  Effect:   ~6 Jcc per typical glibc CRT skeleton are never lifted.
            Visible only as "missing CRT functions in output", not
            as missing user logic. Recursive-descent at L58 already
            walks call edges, but these helpers are not called from
            any discovered function (they're invoked by ELF
            constructors / .init_array indirection).
  Impact:   Cosmetic for the current investigation — even if these
            CRT helpers were lifted, they would not contribute to
            user-meaningful ifs. They would, however, raise the
            apparent if-count and bring the metric above 0.

NOT THE ROOT CAUSE:

  CFG_BUILDER  — verified by reading cfg.rs:195-223. CBRANCH terminators
                 correctly emit ConditionalTrue/ConditionalFalse edges.
                 Working as designed.
  STRUCTURER   — verified by reading structurer.rs:736-740, 1062-1069,
                 and by direct evidence that medium.elf produces 37 ifs
                 from the same code path. Working as designed.
  OUTPUT       — output stage faithfully renders whatever the structurer
                 emits; no if-suppression observed. Working as designed.

================================================================================
5. WHY MEDIUM.ELF WORKS DESPITE THE BUG
================================================================================

medium.elf is compiled at -O2, which:
  - Performs aggressive function inlining (so f_loop_factorial,
    f_branch_max, etc. live inside main).
  - Prefers Jcc over cmov for non-trivial control flow because branch
    prediction is usually a win for medium-length basic blocks.
  - Still emits some cmov for cheap two-way selects (8 cmov in this
    binary), but the dominant control flow is Jcc-based.

Result: 108 Jcc → many CBRANCH IR instructions → 37 structurer ifs.
The 8 cmov silently vanish, but they're a small fraction; the user
sees a mostly-correct decompilation.

debug_calls.elf is compiled at -O0 with -g, which:
  - Disables inlining (each helper compiled as a separate function).
  - Forces stack-spilled parameter handling (mov %edi,-0x4(%rbp);
    mov -0x4(%rbp),%eax …) — visible in every function output as
    the "v1 = 0LL ; *(_QWORD *)(0LL) = …" garbage. That garbage is
    a separate analysis bug (spill/reload + memory-aliasing failure
    in the variable-merge / mem2reg passes), not part of P7-0.
  - GCC -O0's idiom for `?:` is to emit cmov directly without a
    branch, since at -O0 the front-end barely lowers the ternary
    before handing it to the back-end. Hence 100% of user-code
    conditionals become cmov.

So the fixtures specifically stress the cmov path that medium.elf
mostly avoids.

================================================================================
6. RECOMMENDATIONS
================================================================================

R1 (must-fix): Lower Cmov* in lift.rs to either CBRANCH-based control
   flow or a dedicated select primitive. Reuse jcc_condition() to map
   condition codes; it already handles every Cmov suffix (e/ne/b/ae/
   a/be/l/ge/g/le/s/ns).
   Estimated touch points:
     - lift.rs:275-280   (re-route Cmov to a new lift_cmov)
     - ops/control_flow.rs   (factor jcc_condition or add lift_cmov here)
     - ops/data_move.rs   (remove Cmov from lift_mov's mnemonic set)

R2 (nice-to-have, lower priority): Always run prologue scan in addition
   to symbol scan, deduplicating by address. This recovers unnamed CRT
   helpers and would also help stripped binaries that retain partial
   symbols. No user-visible win for P7-0 but cleans up "missing CRT
   functions" reports.

R3 (orthogonal, do NOT bundle here): The "v1 = 0LL" garbage seen in
   every -O0 function body is a separate analysis bug — almost certainly
   a stack-slot / memory-region tracking failure that prevents
   load-from-spill from being threaded back to the spilled value. This
   is beyond P7-0's scope but worth filing as P7-2 or similar.
