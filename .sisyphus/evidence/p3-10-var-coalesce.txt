P3-10: Improved variable coalescence via interference graph
============================================================

TASK
----
Replace the previous "merge SSA versions of same base Varnode" pass with an
interference-graph coalescer that also merges DIFFERENT unique base varnodes
whose live ranges are disjoint and whose inferred types match (mirrors how
IDA Hex-Rays reuses `v3`, `v4`, etc. across unrelated subexpressions).


FILES MODIFIED
--------------
crates/unlace-passes/src/variable_merge.rs   (208 -> 891 lines)
crates/unlace-passes/src/lib.rs              (no change required)
crates/unlace-cli/src/pipeline.rs            (reordered passes)


PIPELINE REORDER
----------------
Old: ExpressionTreePass -> VariableMergePass -> run_type_infer_bounded
New: ExpressionTreePass -> run_type_infer_bounded -> VariableMergePass

Justification: the new VariableMergePass partitions Unique-base varnodes by
inferred PrimitiveType.  Type inference must run first or all uniques would
collapse into the PrimitiveType::Unknown bucket, masking type conflicts.


ALGORITHM
---------
1. Collect every SsaVarnode appearing in `var_map` and `phi_map`.
2. Compute live ranges via standard backward dataflow:
     live_out(b) = (union over succ in successors(b)) live_in(succ)
                   union phi_use_out(b)
     live_in(b)  = use(b) union (live_out(b) - def(b))
   Then for each block, walk right-to-left maintaining `live_after`,
   marking every program point where each varnode is live.
3. Two-level clustering:
   a) Per-base super-cluster: every SSA version of one base Varnode goes
      into the SAME cluster (preserves rax = rax across versions).
   b) Cross-base coalescing (Unique only): super-clusters of different
      Unique bases are merged when (size, inferred type) match AND their
      unioned live ranges do not interfere.  Greedy first-fit.
4. Assign deterministic v1, v2, ... names per cluster.

Detection rules verified by tests:
  - Same primitive type AND same size: REQUIRED
  - Non-overlapping live ranges: REQUIRED
  - Stack varnodes never coalesce (explicit storage)
  - Register varnodes never coalesce across distinct physical registers
  - SSA versions of the SAME base always share a name (storage = same)

FIXTURE: medium.elf
-------------------
End-to-end variable count in C output (`grep -cE "v[0-9]+"`):
  Before: 377 lines, 26 unique v# names
  After : 377 lines, 26 unique v# names

Caveat: the C printer (crates/unlace-output/src/c_printer.rs) currently
manages its own variable-naming scheme via `PrintCtx::name_of` and does NOT
yet consume `SsaFunction::merged_names` produced by this pass.  Wiring the
printer to consume `merged_names` is a follow-on task (Wave 2) which the
P3-10 task description explicitly forbids touching:

    "Do NOT touch structurer.rs or c_printer.rs (other Wave 2 tasks)"

The end-to-end output counts are therefore unchanged; the *structural*
improvement is observable inside `merged_names` itself.

Pass-level cluster reduction observed via tracing on medium.elf:

  func=main           ssa_vars=1239  clusters=45    (baseline=45,  same)
  func=_start         ssa_vars=29    clusters=15    (baseline=17,  -2)
  func=f_rec_fib      ssa_vars=1304  clusters=47    (baseline=47,  same)
  func=f_ackermann    ssa_vars=1221  clusters=43    (baseline=43,  same)
  func=f_rec_power... ssa_vars=323   clusters=31    (baseline=31,  same)

The new pass is at least as good as the baseline on every function and
strictly better on _start.  It does not regress any function because:
  - SSA versions of the same base still share a name (rule 3a).
  - Different bases of incompatible types or interfering ranges stay
    distinct (rule 3b).

The dramatic 3->1 cluster reduction demanded by the task spec is provable
on synthetic IR (test_chain_coalesce) but observable in the real fixture
only on functions with simple, sequential lifter temporaries (most of which
have already been folded into expression trees by ExpressionTreePass).


REFERENCE INSPECTION (IDA hex-rays dumps)
-----------------------------------------
$ ls references/hexrays/ida_dump/hexx64/all/ | wc -l
13000+ files

Sample sub_2ADAB0.c shows the IDA pattern this pass emulates:

    __int64 v2; // r15            <- mapped from register r15 (1 cluster)
    unsigned __int64 v3; // rax   <- rax across whole function (1 cluster)
    unsigned int v5; // ebx       <- ebx across whole function
    int v6; // edx                <- edx across whole function
    __int64 v7; // rax            <- DIFFERENT rax slot, IDA reused v7

Per-function hex-rays comments show v# numbers reused across distinct
liveness windows (the `// rax` annotation shows multiple distinct
SSA-version groups all named `v3`/`v7`/...).  Our implementation does the
same partitioning at the SSA level via interference-graph coalescing.
