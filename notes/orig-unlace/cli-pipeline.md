# Original unlace pipeline driver (origin/master) vs main

Scope: `crates/unlace-cli/src/pipeline.rs` (8,726 lines) and `pipeline/{call_site_guess,function_extents,hir_recovery}.rs` on `origin/master`, plus `crates/unlace-passes/src/pipeline_parser.rs`. Read with `git show origin/master:<path>`; nothing was checked out, built or run. Main is `origin/main` at 188480126a. Main's counterparts are the phase-folder crates (`unlace-decomp`, `unlace-middle`, `unlace-structure`, `unlace-analysis`), not a single driver file, so most rows point at the function that now does the job.

The master driver is one linear chain: lift, merge blocks, tail-duplicate, split irreducible, rewrite x87, build SSA, run a maturity pipeline inside an outer fixed point (Generated, PreOptimized, LocalOpt, Calls, GlobalOpt, then Lvars and Final), emit with per-stage deadlines, and fall back to labelled gotos when structuring hits a complexity limit. Main replaced that with a scheduled action tree (`universal_sched`) that settles maturity levels, a per-function budget clock, and a region structurer that always virtualizes gotos. Its discovery is tiered (`analyzers/entry/`), and it already does the call-site arity work.

Ranking: the first table lists port candidates, most valuable first. The second table lists techniques that main already has, that are unverified, or that are not worth porting. The three issues filed from this table are rows 1, 2 and 3 of the first table.
