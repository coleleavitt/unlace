# Xtensa

The base Xtensa module (`Xtensa:LE:32:default`, `Xtensa:BE:32:default`) is the vendored Ghidra
one. unlace adds the ESP32-S3 variant for #98, and changes the zero-overhead loop handling
(`xtensaMain.sinc`, `xtensaArch.sinc`, `xtensaInstructions.sinc`, below).

## Zero-overhead loops (local change)

Upstream set `loopMode` without `globalset`, so it never reached the loop body. Its
`loopMode=1` root constructor would branch back to `LBEG` after every instruction, and in
practice a `LOOP` body ran once. `LOOP`, `LOOPGTZ` and `LOOPNEZ` now mark `LEND` (the
instruction after the body) with context: `loopEnd`, and `loopDist` = `LEND - LBEG`.
Reaching `LEND` with `LCOUNT` non-zero counts down and branches directly to the loop start
before `LEND` executes, so a counted loop decompiles as `do`/`while`. The `PS.EXCM`
exception-mode test of the hardware is not modelled. `loopMode` is removed.

## L32R target (local change)

`L32R` computes its literal address in 64-bit disassembly arithmetic, so the one-extended
offset carried into bit 32. The operand printed as `0x4003c04d0` for a literal at `0x3c04d0`.
The address is now masked to 32 bits. The p-code was already right, because the space truncates.

## ESP32-S3 PIE (`Xtensa:LE:32:esp32s3`)

The Xtensa LX7 core of the Espressif ESP32-S3 with its Processor Instruction Extensions (the
`EE.*` vector, accumulator and FFT instructions). No prior SLEIGH description of them existed.

Sources: Espressif's LLVM description of the ESP32-S3 DSP instructions,
`llvm/lib/Target/Xtensa/XtensaS3DSPInstrInfo.td` (Apache-2.0 with LLVM exception, branch
`release/esp_23.x`) for the encodings and operand fields, its `XtensaOperands.td` for the
immediate ranges and scales, and its disassembler for the length rule (24-bit TIE words have
op0 bit 3 clear, 32-bit ones set); the ESP32-S3 Technical Reference Manual (chapter
"Processor Instruction Extensions") for the register file and the operations.
`xtensa_esp32s3_pie.sinc` and `xtensa_esp32s3_pie_defs.sinc` were generated from the
TableGen file: one constructor per instruction (213: 124 24-bit, 89 32-bit) and one operand
table per field layout.

Modelled:
- `q0`..`q7` (128-bit), `ACCX`, `QACC_H`, `QACC_L`, `UA_STATE`, `SAR_BYTE`, `FFT_BIT_WIDTH`.
- Exact: `EE.ANDQ`, `EE.ORQ`, `EE.XORQ`, `EE.NOTQ`, `EE.ZERO.Q`/`.ACCX`/`.QACC`,
  `EE.MOVI.32.A`/`.Q`, `EE.VLD.128`, `EE.VST.128`, `EE.VLD.H/L.64`, `EE.VST.H/L.64`,
  `EE.LDF.64/128`, `EE.STF.64/128` (addresses rounded down to the access size), and every
  address-register update: `.IP` adds the scaled immediate, `.XP` adds `ad`, `.INCP` adds 16,
  `.DECP` subtracts 16; the load and store halves of the fused `.LD.*`/`.ST.*` forms.
- The vector arithmetic, compares, multiply-accumulates, shifts, zips, FFT butterflies and the
  accumulator/state loads and stores are named p-code operations (`ee_vadds_s8`, ...) over their
  register operands, writing each output register (and the accumulator they update).

Gaps:
- Saturation and lane semantics of the named operations are not expanded into p-code.
- The PIE state registers are separate from the `user` registers RUR/WUR name.
- The variant drops the generic `cust0`/`cust1` and FLIX placeholders, whose encodings PIE
  occupies.
- Cadence HiFi 2/3/4/5 audio-DSP instructions are not covered: their encodings are per-core
  generated TIE/FLIX tables with no public description.

Checked: every one of the 213 encodings, with random operand values over five passes,
disassembles to its own mnemonic and length; the CLI test images (base instructions from
`llvm-mc`, EE words encoded from the TableGen fields) decompile to the expected loop.

## HiFi 4 of the NXP i.MX RT700 (`Xtensa:LE:32:hifi4_rt700`)

The Cadence HiFi 4 DSP core of the NXP i.MX RT700, with its FLIX bundles and `AE_*` operations.
`xtensa_hifi4_rt700.sinc` and `xtensa_hifi4_rt700_defs.sinc` are generated by
`tools/gen_xtensa_hifi.py`. The input is the core's ISA description: `xtensa-modules.c` and
`xtensa-config.h` from the Zephyr SDK overlay `overlays/xtensa_nxp_rt700_hifi4/binutils`
(`zephyrproject-rtos/sdk-ng` ea319f670e3e), under the Cadence permission notice that
heads both generated files.

How the generator gets its input: `tools/xtensa_hifi_probe.c`, built against binutils 2.45 with the
overlay copied in, walks the xtensa-isa API and writes JSON. The JSON holds every format with its
decoder mask and slot bit map, every opcode each slot can issue with its fixed bits, and every
operand with its field bits and field-to-value decoding.

Modelled:
- **Formats:** the 88-bit (`ae_format88`, `_2`, `_3`, `_4`) and 48-bit (`ae_format48`, `_2`, `_3`) FLIX
  formats. Each is one root constructor that builds its 2 to 4 slot tables and prints the bundle as
  `{ op; op; ... }`, like objdump. There are 3,662 slot or format constructors in all, including the
  base operations each slot can issue.
- **Registers:** `aed0`..`aed15` (`AE_DR`, 64-bit), `u0`..`u3` (`AE_VALIGN`), `aep0`..`aep3`
  (`AE_EP`). Register groups print as objdump does (`b8:b9:b10:b11`); the first register is the operand.
- **Exact p-code:** the base operations in FLIX slots (arithmetic, logical, shifts, moves, conditional
  moves, min/max, `clamps`, `extui`, loads and stores, `l32r`, the `.w15` branches). Also every
  `AE_*` load and store with a single data register and an `.i`/`.x` (offset), `.ip`/`.xp`
  (post-increment), `.iu`/`.xu` (pre-increment) or `.ic`/`.xc` (circular, through
  `hifi_circular_add`) address: the memory access and the address-register update are exact.
- **The 24- and 16-bit TIE operations** the base module does not decode (`ae_*`, `sigmoid_*`,
  `f64*`, ...) are added. The `cust0`/`cust1` and FLIX placeholders are dropped, as in the ESP32-S3
  variant.

Checked: `tools/xtensa_hifi_vectors.c` emits one bundle per (format, slot, opcode), with the slot nop
in the other slots, at two sets of operand values: 4,151 vectors per set. The 3662 this module
generates (every FLIX bundle and the added 24/16-bit operations) disassemble like the overlay's
`xtensa-elf-objdump` in both sets, in mnemonic, operands and length. Of the 534 base 24/16-bit
operations, 275 print in the base module's own spelling (`rsr a3, SAR` for `rsr.sar a3`).

Gaps:
- The arithmetic, multiply-accumulate, shift, pack and select `AE_*` operations, the aligning loads
  and stores (`ae_la*`/`ae_sa*`) and the state reads and writes are named p-code ops
  (`hifi_<mnemonic>`) over their operands, one per written register. Their lane semantics are not
  expanded.
- A bundle's slots run in slot order. The hardware reads every slot's operands before any slot
  writes, so a bundle whose slots write and read the same register lifts sequentially.
- `loop` in a FLIX slot is a named op, not a zero-overhead loop.
- Other HiFi cores (HiFi 1/3/5 and the other vendors' HiFi 4 builds) have their own encodings. Each
  needs its own overlay and generated language.
